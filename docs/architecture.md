# Architecture

This first wireframe is a dependency-free web application served by Node.js. `src/data.js` holds Keys and lessons separately from the views in `src/app.js`; `src/book-of-mormon.js` maps each supplied Book of Mormon page to one lesson; and `src/first-aid.js` maps the First Aid guide pages. Hash routes provide a public landing page, a signed-in Keys dashboard, Groups, progress, Key, and lesson pages without a routing dependency or server fallback. The Groups route displays seven supplied posters in a responsive two-column grid. The two required posters have accessible badge links positioned over each Key; the five themed posters are previews pending lesson content. First Aid has two opening routes for its badge and certificate, then its cover, followed by 14 required image lesson routes. `src/progress.js` manages account-scoped local step checks and reflections, while completion timestamps are also stored by the account API. A Key's completion date is the latest timestamp among its required lessons. The supplied Group 1 and updated Group 2 reference images provide the Key icons. The supplied Book of Mormon and First Aid pages are the primary lesson content.

The Node server now exposes local account APIs backed by SQLite (`data/accounts.sqlite`, ignored by Git). Tables hold hand-seeded wards, users (with a ward-membership status and a separate bishopric-role request), membership status history, sessions, and lesson completion dates (DEC-012). Session tokens are held in HTTP-only cookies; password hashes use scrypt. The public home route uses a separate Covenant Youth shell, and the client shows Keys, Groups, lessons, and progress only when the account API reports a signed-in, Active member; other members see only their account page. The internal Keys overview is at `#/keys`. Profile milestones are derived from account lesson completion dates. Lesson step checks, reflections, and the Bishopric notification demo state remain browser-local and are scoped by account ID. A browser-only progress import is available on the profile page. The Bishopric role is self-selected for this prototype, so its approval numbers demonstrate the flow but do not verify a real calling or parental consent. The static server blocks access to database files; static lesson assets themselves are not access-controlled. No production authentication provider or hosting platform is selected.

The Bishopric tools preview route (`#/bishopric-tools`) is available only to signed-in, active Bishopric accounts and places the existing standalone mock inside the site shell. The server also restricts the mock HTML file to those accounts. It uses a same-origin frame to keep the mock layout and interaction code isolated during this wireframe phase. The frame resizes to its contents. Its ten fictional requests and status actions are in memory and are not connected to the SQLite account queue. Real ward approval remains a separate implementation step.

The Bishopric reporting concepts route (`#/bishopric-reporting`) uses the same active Bishopric access rule and embeds the existing standalone reporting mock without changing its presentation. The server restricts its HTML file as well. Its fictional year, 50 youth, and all displayed measures remain static demo data; they are not read from the account database or an analytics service.
